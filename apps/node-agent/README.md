# Lab Node Agent

Реализованы read-only Proxmox adapter, CLI `lab-node-agent` и служба `python -m lab_node_agent.service`. Отдельный Python-пакет без runtime-зависимостей, с собственным lockfile для тестов. Читает inventory по проверенному HTTPS с API token; не изменяет гостей. Служба отдаёт снимок только через mTLS с закреплённым сертификатом клиента.

Служба, опрос с VPS и pull-updater установлены на физическом узле; проверенные шаги описаны в [гайде транспорта](../../docs/node-transport.md) и [гайде автообновления](../../docs/node-auto-update.md). Типизированные команды изменения гостей, durable receipts и применение учебных сетей ещё не реализованы; произвольного shell API нет.

[Подготовка установки и границы inventory](../../docs/proxmox-agent-first-install.md).

[План реализации](../../docs/implementation-plan.md).

Wheel 0.3.0 также содержит [локальную диагностику LVM-thin](../../docs/proxmox-storage-probe.md). Она запускается администратором отдельно и не меняет права или поведение установленной службы.

Начиная с 0.8.0 снимок дополнительно содержит имена и порты Linux bridges, прочитанные из Proxmox API. При недоступности этой части остальные наблюдения сохраняются, а в `limitations` появляется `NETWORK_INVENTORY_UNAVAILABLE`. Наличие моста без физического порта само по себе не подтверждает изоляцию; `admission_ready` остаётся `false`.

Для будущей сверки задач добавлено внутреннее чтение конфигурации конкретной QEMU VM или LXC по типу и числовому VMID. Метод не публикуется в mTLS endpoint и не меняет гостя; произвольный путь Proxmox API передать ему нельзя. Признание машины принадлежащей Lab Manager потребует проверки метки владения и сохранённой записи в БД, а не одного совпадения VMID.

Начиная с 0.14.0 снимок каждого гостя содержит `ownership_marker`, прочитанную из его конфигурации. Допускается только точная метка `lab-manager:runtime=<UUID>;generation=<N>`; посторонние описания передаются как отсутствие метки, а повреждённая метка Lab Manager останавливает публикацию снимка. Поле `ownership` остаётся `UNVERIFIED`: VPS должен сопоставить метку с собственной долговременной записью. Допуск новых машин остаётся закрытым.

Версия 0.9.0 содержит команду `lab-node-policy <config.json>`, которая только выводит nftables-правила в stdout. Конфигурация — массив записей `{"bridge":"lmbrgroup1","mode":"GROUP_LAN"}` или `{"bridge":"lmbrsolo1","mode":"ISOLATED"}`. Разрешается L2-обмен только на явно перечисленных общих мостах; host, routed и Internet-трафик по-прежнему блокируются. Команда не устанавливает правила и не открывает допуск машин. Установленные правила на Proxmox этим выпуском не меняются.

Версия 0.10.0 добавляет root-only `lab-node-segment` для локального создания и удаления **пустого выключенного** Linux bridge по ID выделения сети. При создании записываются тип сети и подсеть, имя моста выводится из ID, ownership закрепляется через alias; повтор команды не создаёт второй мост. Удаление отказывается, если у моста есть порт, IP-адрес, состояние UP или чужой alias. Данные хранятся атомарно в `/var/lib/lab-manager-node/segments/segments.json`, отдельном root-only подкаталоге: права существующего каталога storage-снимков не меняются. Команда не подключена к mTLS endpoint, не назначает gateway, не включает bridge, не присоединяет VM/LXC и не применяет nftables-правила. Использовать её для реальных занятий до завершения сетевого шлюза и командного протокола нельзя.

Версия 0.11.0 добавляет типизированный `ProxmoxLxcProvider` для первого сценария Debian LXC. Он принимает только Debian `vztmpl`, хранилище и учебный мост `lmbr*`, создаёт непривилегированный контейнер остановленным с выключенным сетевым линком, SSH-ключом и меткой `Runtime`/generation. Повтор создания с тем же VMID не делает второй запрос; чужой VMID не принимается. Start/shutdown сначала сверяют метку и безопасные свойства конфигурации, а результат операции остаётся Proxmox task ID до проверки статуса. На целевом узле уже имеется шаблон Debian 13; точный volume ID не зашит в код. Это пока **адаптер без маршрута из VPS**: write-token, durable command receipts, настройка сети и Guacamole ещё нужны до запуска пользовательской машины.
