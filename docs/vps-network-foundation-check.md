# Закрытие подготовительного сетевого этапа на VPS

Этот этап проверяет адресный пул и исправную поставку учёта подсетей. Он **не** разрешает создание гостевых машин: на Proxmox по-прежнему `admission_ready=false`, а реальная изоляция `ISOLATED`/`GROUP_LAN` будет проверяться в следующем этапе на гостях.

После успешного CI и очередного автоматического обновления `dev-vps` выполнить в root shell VPS **одну команду**:

```bash
python3 /opt/lab-manager/repo/tools/verify-vps-network-foundation.py
```

Скрипт только читает состояние. Он не печатает `.env.vps`, ключи mTLS или токены и не меняет Docker, маршруты, БД либо systemd. Ожидаемый итог — `Result: PASS (7/7 checks)`.

Проверяются:

1. Отсутствие пересечения предложенного учебного пула с полными IPv4-маршрутами и адресами VPS, а также с Docker IPAM. Маршрут `default` не считается занятым локальным диапазоном.
2. Активный Git SHA совпадает с состоянием updater; нет незавершённой операции, timer включён, последний запуск успешен.
3. PostgreSQL, Redis, API, web и worker здоровы; образы приложений совпадают с активным выпуском.
4. База, API и worker используют одну миграцию `0007_network`; локальный и публичный HTTPS readiness отвечают `ready`.
5. Свежий снимок Proxmox доступен worker через mTLS; management-мост имеет физический порт, учебный мост не имеет; допуск гостевых машин остаётся закрытым.
6. На VPS остаётся не менее 1.5 GiB для следующего обновления.

Результат `FAIL` указывает конкретный пункт. При `FAIL Updater` и наличии `pending.json` нельзя вручную удалять pending-запись или архив миграции: сначала требуется разобрать состояние БД и работающих контейнеров. Проверки сетевого guard на Proxmox уже выполнялись отдельно и описаны в [сетевом гайде](networking.md); этот VPS-скрипт их не повторяет.

Адресный пул скрипта по умолчанию — предложенный для этой инсталляции. Для другой инсталляции используются `--pool`, `--management-bridge` и `--guest-bridge`; пароль или адрес публичного сервиса в командную строку не передаются.
