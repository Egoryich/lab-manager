# Надёжные фоновые операции

Реализованный срез D3: очередь PostgreSQL, отдельный worker и фоновая проверка конфигурации окружения. Это ещё не запуск машин, admission или календарь бронирования.

`POST /api/environments/{id}/validate` принимает `request_id` и `expected_version`, возвращает 202 и Operation. Только владелец с ролью Teacher может поставить проверку. Job, audit и outbox-факт фиксируются одной транзакцией. Повтор того же запроса возвращает ту же операцию; другое тело с прежним ключом получает 409. Уникальный частичный индекс запрещает две незавершённые операции одного окружения.

Worker забирает работу через `FOR UPDATE SKIP LOCKED`, выдаёт lease на 30 секунд и увеличивает fencing generation. Время берётся из PostgreSQL. Запись результата требует совпадения worker ID, поколения и ещё действующего lease; старый процесс не может завершить повторно захваченную работу. Один worker выполняет одну проверку за раз, использует одно соединение БД и ограничивает время обработки 20 секундами. Ошибки повторяются с задержкой, не более пяти попыток.

Автоматическое повторное выполнение после истечения lease разрешено **только** `ENVIRONMENT_VALIDATE`: этот обработчик читает конфигурацию и не имеет внешних эффектов. Будущие команды Proxmox/Tuya требуют отдельных receipts, checkpoints и reconciliation. Неизвестные kinds этот worker не выполняет; exactly-once для внешней инфраструктуры не заявляется.

Перед проверкой заново читаются статус пользователя, роль, актуальная политика, принадлежность окружения, версия и состав группы. Результат сохраняет время, revision политики и расчёт Student + Demo. `SUCCEEDED` означает завершённую проверку; превышение квот отражено внутри `estimate`, а не выдано за разрешение запуска. Ответ явно содержит `CONFIGURATION_ONLY`, `reservation_created=false`, `admission_status=NOT_CHECKED`.

`GET /api/operations` и `GET /api/operations/{id}` доступны владельцу и Admin; Student не получает доступ. Список отсортирован от новых к старым, курсор — ID последней полученной операции. В DTO нет worker IDs, lease, внутренних request digests и текста исключений. Интерфейс опрашивает незавершённую операцию и восстанавливает последний результат после перезагрузки страницы.

`operation_events` — транзакционный outbox фактов изменения состояния с уникальностью `(operation_id, version)`. Доставка SSE/Redis ещё не подключена. Будущий consumer должен учитывать возможный иной порядок commit, не использовать один максимальный sequence как доказательство доставки всех меньших номеров. Сейчас worker опрашивает сами durable jobs; потеря Redis не уничтожает и не освобождает их.

`GET /api/admin/worker-status` сообщает свежесть heartbeat; доступен только Admin. Docker healthcheck читает локальную отметку успешного цикла worker, отдельным лёгким процессом Python. API readiness проверяет схему/БД/Redis, а не обещает готовность Proxmox.

## Запуск

После миграции `0003_operations`:

```bash
uv run python -m lab_manager.worker
```

Для одной итерации обработки:

```bash
uv run python -m lab_manager.worker --once
```

На VPS используется тот же immutable API-образ, отдельный контейнер `worker`, без опубликованных портов, лимит 128 MiB. Переход существующей установки описан в [гайде выпуска worker](vps-worker-rollout.md). Пул ресурсов, сохранение дисков, Run/Runtime, календарь и реальные адаптеры остаются следующими задачами.
