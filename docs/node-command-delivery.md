# Доставка команд LXC с VPS

Миграция `0009_commands` и worker добавляют постоянную запись команды до
сетевого запроса к Proxmox. У каждой команды есть UUID, привязка к операции
занятия, конкретной машине и узлу, точный JSON, состояние, время первой
попытки и ответ агента. В один момент у машины может быть только одна
незавершённая команда.

Worker перед отправкой один раз фиксирует `ATTEMPTED` в PostgreSQL. После
этого он может только читать ответ агента по UUID; повторный POST он не
отправляет. При потере ответа, отсутствии записи в журнале агента или
неудаче задачи Proxmox команда остаётся для ручной сверки. Это может оставить
занятие незапущенным, но не создаст второй контейнер поверх первого.

API уже принимает бронирование занятия, а worker хранит и сверяет команды.
Выход к командному endpoint Proxmox не активируется одной только миграцией.
Перед первым реальным занятием нужны: отдельный write token Proxmox с
ограниченными ACL, журнал агента, проверка этих прав реальным тестовым LXC,
доступная Guacamole сеть и проверка резерва CPU/RAM/disk.

Миграция `0009_commands` уже установлена на VPS; текущую ревизию проверяет
`tools/verify-vps-network-foundation.py`. Не следует вручную вставлять команды
в БД: их формирует транзакция занятия вместе с правами и резервом.

Аппаратная проверка исходного пути уже выполнена на Proxmox: временный Debian
13 LXC создался в `student-lvm`, запустился, подтвердил SSH, остановился и был
удалён вместе с диском и изолированным мостом. Предупреждение о systemd 257
не помешало запуску; включать LXC nesting для этого не потребовалось.

При запуске созданного LXC агент сначала проверяет работающую сетевую защиту,
затем снимает `link_down=1` с `net0` через API Proxmox и только после повторной
сверки конфигурации отправляет команду запуска. Для этого выделенному write
token требуется `VM.Config.Network` на управляемых VMID в дополнение к правам
создания и питания. Пока отдельный допуск SSH не применён, защитные правила
Lab Manager блокируют трафик учебного моста. Ошибка изменения `net0` оставляет
команду в состоянии для ручной сверки; повторный POST не выполняется.

### Включение команд на Proxmox

Инвентарный токен остаётся только для чтения. После успешного обновления агента
отдельный [установщик](../tools/enable-node-commands.sh) создаёт пул
`lab-manager`, отдельного пользователя и privilege-separated токен. Роли
разнесены по пулу гостей, учебному диску, локальному каталогу шаблонов и
локальным мостам. Установщик сверяет эффективные права токена, сохраняет его
значение только в root-owned файле, подключает файл как systemd credential
через отдельный drop-in и создаёт постоянный журнал команд. Значение токена
не выводится. Если активация агента не удалась, прежняя конфигурация
возвращается, а drop-in удаляется;
созданную учётную запись надо проверить отдельно до повтора установки.

Запускать под root после автообновления агента до версии `0.18.0`. На Proxmox
checkout репозитория не требуется: скачать установщик из закреплённого коммита,
сверить опубликованный SHA-256 и выполнить `bash /tmp/lm-enable-node-commands.sh`.
Установщик не создаёт LXC. Если он прервётся после создания пользователя или
токена, повторный запуск не пройдёт предварительные проверки; сначала нужно
осмотреть оставшиеся объекты.

После сообщения `PASS` проверить `systemctl is-active lab-node-agent.service`
и `systemctl show lab-node-agent.service -p Result -p ExecMainStatus`. Перед
первым занятием нужен отдельный тестовый LXC через этот токен, поскольку права
Proxmox проверяются и в самом API создания контейнера. [Модель ACL Proxmox](https://github.com/proxmox/pve-docs/blob/master/pveum.adoc).
