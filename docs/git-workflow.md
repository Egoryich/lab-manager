# Ветки и выпуск Lab Manager

Один репозиторий содержит обе части системы и общие контракты.

| Ветка | Назначение |
|---|---|
| `main` | Проверенное совместимое состояние VPS и Proxmox. Стабильность реализованных функций не означает готовность всего продукта. |
| `dev-vps` | API, worker, frontend, база данных и развёртывание на VPS. После настройки доставки успешные проверки запускают обновление VPS. |
| `dev-proxmox` | Node Agent, интеграция Proxmox, гостевые сети и инфраструктура физического сервера. |

## Работа с изменениями

1. Изменения выполняются в ветке соответствующей части. Общие контракты и форматы команд согласуются между обеими ветками.
2. Все ветки проходят CI: миграции, backend-тесты на PostgreSQL/Redis, проверки кода и контракта, сборка frontend и браузерные сценарии.
3. Изменение протокола сначала добавляет совместимую поддержку на принимающей стороне. Удаление старого формата допускается после обновления обеих сторон. Миграции имеют уникальную согласованную историю; конфликты Alembic устраняются до выпуска.
4. В `main` объединяется проверенное состояние через pull request. Перед слиянием проверяется итоговый набор обеих частей, включая интеграционные сценарии затронутой инфраструктуры. Локальные HTTP-тесты не заменяют проверки Proxmox и Guacamole.
5. После выпуска изменения из `main` переносятся в обе development-ветки обычным merge. Общая история сохраняется; force-push для синхронизации не используется.

## Доставка и секреты

Создание веток не включает автоматическое развёртывание. Workflow выполняет проверки, а для `dev-vps` дополнительно собирает, проверяет в Compose и публикует образы API/web с тегом полного SHA. [Первое развёртывание](vps-first-install.md) пользователь выполняет вручную без SSH-доступа ассистента. [Pull-updater](vps-auto-update.md) после установки timer на VPS забирает только проверенный текущий SHA, сериализует обновления и проверяет готовность. Изменение миграций или Compose требует ручного выпуска; после ручного выпуска worker автоматически обновляются совместимые API/web/worker контейнеры. API и worker используют один образ.

Пароли, SSH-ключи, Tuya secrets и фактический inventory не хранятся в Git. Секреты доставки настраиваются отдельно. Сам факт подключения GitHub не предоставляет приложению доступ к VPS или Proxmox.

При первоначальном создании трёх веток они имеют одинаковую базу существующего проекта. Прежняя `master` сохраняется для истории; дальнейшая разработка использует согласованные ветки. Основной веткой GitHub следует назначить `main`; защита слияний и обязательные CI checks настраиваются в GitHub отдельно.
