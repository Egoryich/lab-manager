# Выбор размеров машин в окружении

Основание: обсуждение с пользователем о профилях и политиках. Реализация подготовлена в `dev-vps`, выпуск требует миграции `0005_sizing` и ручного принятия VPS updater. До подтверждения установки на VPS команды ниже описывают код, а не состояние рабочего сайта.

Администратор регистрирует неизменяемую версию профиля с рекомендуемыми RAM, vCPU, диском и необязательными нижними/верхними границами. Если границы не указаны, они равны рекомендуемым размерам; все ранее созданные версии профилей при миграции остаются фиксированными. Выбор образа ОС, сетевого режима и доступа в Интернет остаётся свойством версии профиля. CPU-милликредиты по умолчанию равны `vCPU × 1000`; это учётная стоимость, а не наблюдаемая загрузка. Администратор может задать особую стоимость через API. При выборе другого числа vCPU стоимость масштабируется пропорционально исходной стоимости профиля с округлением вверх.

Преподаватель выбирает разрешённый профиль студента и демо, затем отдельно задаёт размеры каждой машины в границах соответствующего профиля. Backend проверяет границы повторно; подделанный браузерный запрос их не обходит. Расчёт умножает студенческие размеры на актуальный состав группы, добавляет одну демо, учитывает диски и минимальные файлы RAM-state для QEMU. Сохранённое подготовленное окружение закрепляет оба набора размеров; повтор того же `request_id` с иными размерами возвращает конфликт. Worker при проверке конфигурации использует сохранённые значения, а не новые рекомендуемые размеры из каталога.

Профиль задаёт размеры одной машины; политика преподавателя задаёт отдельный верхний предел его использования. Реальная вместимость Proxmox и пересекающиеся брони — третий, независимый предел. Сейчас API возвращает `admission_status=NOT_CHECKED` и `reservation_created=false`: уменьшение размеров позволяет исправить превышение разрешённой политики, но не обещает свободную RAM или диск на сервере. Запуск машин остаётся выключен до ресурсного ledger, подтверждённой полноты inventory и транзакционного admission. Права на расширенные изменения после создания Runtime, обновление образа, календарь и реальные операции Proxmox — отдельные следующие этапы. Текущая форма выбора внутри диапазона не опирается на будущий `can_override_resource_limits`.

Миграция добавляет границы в `profile_versions` и выбранные размеры в `environments`. Для существующих строк она переносит текущие значения без изменения самих профилей и окружений. Старые API-запросы без `student_resources`/`demo_resources` продолжают использовать рекомендуемые значения профилей. В локальном PostgreSQL отдельно проверены обновление существующей схемы и сохранение прежних размеров; интеграционный сценарий проверяет диапазоны, вычисление, идемпотентность и повторную проверку worker.
