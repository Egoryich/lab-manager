# Календарь и резервирование времени

Основание: DEC-08/09 из [decisions.md](decisions.md). Пользователь разрешил календарь с очередностью бронирования и отменой своей брони. Ниже — предлагаемая техническая конкретизация; она не исключает одновременную работу нескольких Teacher, если ресурсов достаточно.

## Что видит преподаватель

Собственные Environment, свои брони и свободные/недоступные интервалы для выбранного профиля и числа студентов. Нет имён других Teacher, названий чужих групп, roster, Runtime, состояния их работы или чужих booking IDs. Admin видит полную картину.

Если запустить занятие нельзя, сообщение: «Для этого окружения сейчас недостаточно свободных ресурсов», с предложением ближайшего доступного времени. API/SSE/ошибки не раскрывают, кто именно занял ресурс. Calendar не обещает физическую готовность node при аварии.

## Модель

`ScheduleBooking`: id, owner_teacher_id, environment_id, node_id, starts_at, ends_at, timezone_display, state, accepted_sequence, config_revision, roster_revision, requested compute + demo + overhead, disk_delta_reservation, start/end transition margins, version, cancel reason.

Состояния: `CONFIRMED/STARTING/ACTIVE/ENDING/COMPLETED/CANCELLED/FAILED`. Предварительный расчёт — отдельный read-only preview, не CONFIRMED. Временной интервал полуоткрытый `[start, end)`; UTC в DB, локальная зона только для UI. Значение end включает согласованное время освобождения compute, а не только нажатие кнопки завершения.

`BookingResourceClaim`: booking_id, resource class, interval, amount. Это отдельная сущность от кратковременной `Reservation` операции и постоянной `ResourceAllocation` диска. Бронь в календаре не означает, что выключенная машина потребляет RAM прямо сейчас.

## Гонки и приоритет

1. Под общим Node → Teacher → Storage → Environment lock order проверить policy, конфигурацию, roster и все пересекающиеся подтверждённые брони.
2. Считать максимальную сумму обязательств на границах интервалов; попарной проверки или суммы без временных границ недостаточно.
3. Учитывать реальные активные/неопределённые claims, инфраструктурный reserve, чужие подтверждённые интервалы и лимиты Teacher. Для нужных новых дисков удерживать отдельное disk commitment с момента подтверждения; существующий диск не списывается заново на каждую бронь.
4. Первая успешно закоммиченная допустимая транзакция получает CONFIRMED. Более поздний конфликт получает отказ; timestamp браузера не определяет приоритет.
5. При старте атомарно преобразовать соответствующие interval claims в активные allocations с привязкой к booking_id, без двойного списания. Повторный start не создаёт новый бюджет.

Обычный «запустить сейчас» без предварительной брони также получает bounded interval с end_at и проверяет будущие подтверждённые интервалы. Бессрочный запуск не может занять ресурс, уже обещанный следующему занятию. Изменение числа участников/профиля/длительности брони требует нового admission delta; прежняя бронь не покрывает произвольное увеличение.

## Отмена и завершение

Teacher отменяет только собственную будущую бронь. Освобождаются её compute interval claims и доказанно неиспользованные disk reservations; существующие данные не удаляются. Повтор отмены идемпотентен.

Для ACTIVE вместо тихой отмены используется завершение пары: предупреждение → закрытие сессий → сохранение/выключение по согласованной persistence policy → подтверждение остановки → освобождение compute. До подтверждения claims удерживаются, даже если календарное время истекло.

Переходный запас для сохранения RAM/остановки должен входить в admission заранее. Нельзя обещать следующий слот, предполагая мгновенную hibernation десятков VM. Значения запасов и допустимые длительности определяются по стенду/настройкам Admin. При зависшей предыдущей операции новая бронь отображается как задержанная/FAILED; чужое занятие не получает ложный успешный старт.

Физический node можно включать заранее через Tuya только при разрешении владельца и настроенном lead time. Неопределённый power result не вызывает бесконечные импульсы. Окончание слота не разрешает удаление дисков.

## API и проверки

Предлагаемые routes: `GET /api/availability`, `POST /api/bookings`, `GET /api/bookings`, `GET /api/bookings/{id}`, `POST /api/bookings/{id}/cancel`, `POST /api/bookings/{id}/reschedule`.

Teacher list содержит только свои записи. Availability принимает требуемые ресурсы/профиль, возвращает интервалы доступности без чужих объектов. Admin routes отдельно. Все mutations имеют idempotency key и version.

Проверки: две конкурентные заявки на последний объём; частично пересекающиеся интервалы; соседние интервалы с transition margin; отмена/повтор; изменение roster; неизвестный фактический stop; node offline; превышение квоты; отсутствие утечек в REST/SSE/calendar/error. Любая гарантия времени зависит от здоровья оборудования и подтверждённых storage/network возможностей.
