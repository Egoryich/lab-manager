# Основа расчёта вместимости

`apps/api/src/lab_manager/capacity.py` — чистый расчёт для будущего scheduler. Он не выдаёт бронь и не запускает Proxmox. Его входы рассчитаны на конфигурацию администратора, свежий подтверждённый inventory узла и сумму существующих броней под блокировкой resource ledger.

RAM: из физической памяти вычитаются резервы хоста, инфраструктуры и безопасности, RAM внешних запущенных гостей и уже обещанная RAM. Дополнительно запрос должен помещаться в наблюдаемую свободную память после safety reserve. Swap не добавляет ёмкость. CPU учитывается в милликредитах; коэффициент oversubscription задаётся политикой, а не берётся из процента текущей загрузки.

Storage: для выбранного пула вычитаются минимум 10% полного объёма, логические обязательства внешних дисков и уже обещанные диски/файлы гибернации. Диски остановленных окружений продолжают занимать бюджет; RAM/CPU учитываются по пересекающимся занятиям. Одновременно проверяется физически доступное место. Для LVM-thin требуется безопасное заполнение metadata. `local` и `local-lvm` на одном SSD нельзя представлять как два независимых физических пула; mapping общей основы ещё надо добавить в подтверждённый inventory и настройку scheduler. Расчёт не суммирует их автоматически.

При устаревшем inventory, `admission_ready=false`, неизвестном владении гостей, неполной сверке дисков или отсутствии thin metadata результат блокирует допуск с явными кодами причин. Текущий Proxmox agent сообщает `admission_ready=false`, `thin_metadata_percent=null`, `ownership=UNVERIFIED`, поэтому **никакие занятия через этот расчёт сейчас не допускаются**. Данные, присланные пользователем командой `lvs`, являются диагностическим снимком и не превращают непрерывный agent inventory в доверенный источник.

Теперь схема `0006_ledger` хранит политику узла, единственную строку блокировки на узел, постоянное обязательство по диску окружения и ограниченную временем бронь CPU/RAM. Внутренний сервис при бронировании блокирует строку узла через `SELECT ... FOR UPDATE`, проверяет свежий inventory, складывает пересекающиеся занятия и все сохранённые диски и фиксирует оба обязательства в одной транзакции. Повтор запроса по его ID идемпотентен; отмена будущего занятия освобождает CPU/RAM и удаляет только ещё не созданный диск, который не нужен другим занятиям. Миграция не создаёт политики и брони автоматически.

Публичный API бронирования и календарь ещё не подключены: нужны проверка прав, состава группы и версии окружения, а также способ администратора задавать политику узла. Agent пока не подтверждает ownership, дисковые обязательства, физическую основу storage и thin metadata. Поэтому даже внутренний сервис с текущим узлом отказывает в допуске; `Environment` остаётся DRAFT, API возвращает `reservation_created=false` и `admission_status=NOT_CHECKED`, машины не запускаются.
